\section{Herramientas externas utilizadas}

Las diferentes herramientas que el equipo utilizo para el desarrollo del MVP, va desde bases de datos, lenguajes de programación, 
herramientas de virtualizacion, librerías, \textit{frameworks}, motores para desarrollo continuo y computación en la nube. 
A continuación mencionamos todas ellas:
\vspace{0.25cm}

\textbf{\underline{Unity}}: Para el desarrollo del Editor de Mundos y el Juego (Servidor/Cliente) se optó 
por el motor \textit{Unity}, principalmente por su curva de aprendizaje accesible, 
su amplia comunidad y la gran disponibilidad de tutoriales, documentación y herramientas de terceros. Entre 
las desventajas encontradas se destacan la dificultad de integración con algunas herramientas externas, el 
costo de ciertos recursos de pago (\textit{Assets que fueron comprados para mejorar la calidad del juego en terminos de UX/UI}), 
la complejidad del manejo del LSP de .NET subyacente y el impacto en el  rendimiento local del proyecto a medida que este crecía en tamaño y complejidad.
Se consideró \textit{Godot} como alternativa, pero fue descartado en favor de \textit{Unity} debido a su 
mayor madurez como plataforma, su ecosistema más consolidado y la mayor disponibilidad de documentación 
y recursos de aprendizaje.

\textbf{\underline{Mirror}}: Para la implementación de la funcionalidad multijugador en el juego, 
se utilizó la librería \textit{Mirror} para Unity. Se optó por \textit{Mirror} en lugar de 
\textit{Netcode for GameObjects} (la solución oficial de Unity) debido a su naturaleza de código abierto 
y su mayor flexibilidad en el transporte de red, que permite intercambiar  la capa de transporte (por ejemplo, KCP sobre UDP para baja latencia) 
según las necesidades del proyecto. Además, \textit{Mirror} no impone un límite de usuarios concurrentes (CCU) y presenta un mayor 
\textit{throughput} bruto, lo que lo hace más apto para soportar una cantidad elevada de jugadores 
simultáneos, una característica especialmente relevante para un juego del género \textit{MMO} como el desarrollado. 
Esta flexibilidad y su enfoque modular resultan particularmente convenientes para una arquitectura con 
servidor dedicado y lógica autoritativa.

\vspace{0.25cm}

\textbf{\underline{VContainer}}:
Para la gestión de dependencias en el proyecto, se optó por la librería de inyección de dependencias \textit{VContainer}.
Esta herramienta permitió organizar el código de manera más modular y desacoplada, facilitando la escalabilidad y mantenibilidad del proyecto. 
Lo que permitió al equipo implementar patrones de diseño como la inversión de control y la inyección de dependencias de manera eficiente.

\vspace{0.25cm}

\textbf{\underline{GLTFast}}: 
Esta herramienta permitió importar modelos en formato \textit{.glb} de forma eficiente, con soporte para texturas, 
animaciones y materiales.


\vspace{0.25cm}

\textbf{\underline{Golang}}: El equipo decidió utilizar para el desarrollo del core service, el lenguaje de programación 
\textit{Go}. La decision de este lenguaje viene dada por la familiaridad de la mayoría de los miembros del equipo con
es lenguaje. Además queríamos un lenguaje tipado, para garantizar la mínima cantidad de errores y facilitar la detección
de \textit{bugs}. Cuenta además con la posibilidad de utilizar y llevar de manera practica, confiable y segura el uso de librerías
externas para diferentes funcionalidades requeridas. Como la conexión con bases de datos, servicios externos o la posibilidad 
de escribir endpoints de forma rapida, práctica y sencilla.

\vspace{0.25cm}

\textbf{\underline{Gin Gonic}}: \textit{Framework} web HTTP para Go utilizado en el desarrollo del core service. Permite 
definir \textit{endpoints} REST de forma rápida y estructurada, con soporte para middlewares, manejo de rutas y validación 
de parámetros. Se eligió por su alto rendimiento, su amplia adopción en la comunidad de Go y la familiaridad del equipo con 
la herramienta.

\vspace{0.25cm}

\textbf{\underline{Stripe}}: Plataforma de pagos utilizada para gestionar la compra de gemas y el manejo de suscripciones. 
Provee una API robusta y bien documentada que se integró con el core service en \textit{Go}, permitiendo procesar pagos de 
forma segura sin necesidad de manejar datos sensibles de tarjetas directamente. Además permite manejar pagos internacionales, 
lo cual es importante para un producto con alcance global. Es por esto que se descarto alternativas como Mercado Pago.

\vspace{0.25cm}

\textbf{\underline{Python}}: Este lenguaje fue utilizado para realizar todos los scripts que permitieron principalmente: 
Levantar diferentes servicios de forma rapida y \textit{seedear} la base de datos con assets y usuarios. A su vez, se opto 
por este para realizar los tests de aceptación del core service. Ya que la librería de \textit{Go} (\textit{godog}), 
era demasiado ardua y difícil de configurar. Por lo que se opto por utilizar su alternativa en \textit{Python} (\textit{Behave}).

\vspace{0.25cm}

\textbf{\underline{Nomad}}:
Para la orquestación de contenedores y el despliegue de los servidores de mundos, se utilizó \textit{Nomad} de HashiCorp.
Esta herramienta permitió gestionar de forma eficiente el ciclo de vida de los contenedores, incluyendo su escalado automático y la
asignación de recursos en función de la demanda. Se eligió \textit{Nomad} por su simplicidad, 
su integración nativa con otras herramientas de HashiCorp como Terraform y Consul, y su capacidad para manejar cargas de trabajo heterogéneas, lo que se ajustaba a las necesidades del proyecto.

\vspace{0.25cm}

\textbf{\underline{Consul}}:
Para el descubrimiento de servicios y la gestión de la configuración en el clúster de mundos, se utilizó \textit{Consul} de HashiCorp.

\vspace{0.25cm}

\textbf{\underline{Miro, Excalidraw y Figma}}: Herramientas de diseño y colaboración visual utilizadas en distintas etapas 
del proyecto. Miro y Excalidraw se emplearon para la elaboración de diagramas, flujos de arquitectura y sesiones de \textit{brainstorming} 
del equipo. Figma fue utilizado para el diseño de interfaces y \textit{mockups} de las pantallas del juego y el editor de mundos, 
permitiendo iterar sobre el diseño antes de implementarlo.

\vspace{0.25cm}

\textbf{\underline{Inteligencia Artificial Generativa}}: El equipo incorporó herramientas de IA generativa (Claude, ChatGPT, 
Gemini, GitHub Copilot) como asistentes durante el desarrollo. Su uso abarcó la generación de UI, investigación de herramientas 
y soluciones a problemas técnicos, \textit{debugging}, generación de código con moderación y supervisión humana para evitar 
errores o código no óptimo, generación de documentación para los repositorios, revisión de PRs y generación de pruebas unitarias, 
de integración y tests de aceptación.

\vspace{0.25cm}

\textbf{\underline{Datadog}}: Plataforma de observabilidad y monitoreo utilizada para el seguimiento del estado y el 
rendimiento de los servicios en producción. Permite visualizar métricas, logs y trazas distribuidas en tiempo real, facilitando 
la detección y diagnóstico de problemas. Se integró con el core service y la infraestructura en AWS para tener visibilidad 
centralizada del sistema. Se pensó en utilizar otras alternativas como Prometheus y Grafana, pero se optó por Datadog debido 
a su facilidad de integración, su interfaz intuitiva y su capacidad para manejar grandes volúmenes de datos de monitoreo 
sin necesidad de gestionar la infraestructura subyacente.

\vspace{0.25cm}

\textbf{\underline{Terraform}}: Herramienta de infraestructura como código (IaC) de HashiCorp utilizada para provisionar 
y gestionar los recursos en AWS de forma declarativa y reproducible. Permite versionar la infraestructura junto al código 
del proyecto, facilitando la creación de entornos consistentes y auditables sin intervención manual en la consola de AWS.

\vspace{0.25cm}

\textbf{\underline{Bruno}}: Cliente HTTP utilizado para probar y documentar los \textit{endpoints} del core-service durante 
el desarrollo. A diferencia de Postman, Bruno almacena las colecciones de \textit{requests} como archivos locales versionables 
en Git, lo que permitió al equipo compartir y mantener actualizadas las pruebas de API junto al código fuente.

\vspace{0.25cm}

\textbf{\underline{Brevo}}: Plataforma de email marketing y transaccional utilizada para el envío de correos electrónicos 
a los usuarios, como confirmaciones de registro, recuperación de contraseña y notificaciones del sistema, como pagos o cambios en 
la subscripción. Se integró con el core service mediante su API, permitiendo gestionar el envío de emails de forma confiable 
sin necesidad de administrar infraestructura de correo propia.

\vspace{0.25cm}

\textbf{\underline{OSV Scanner}}:
Herramienta de seguridad utilizada para escanear las dependencias del proyecto en busca de vulnerabilidades conocidas.
Se integró en el pipeline de CI para ejecutar análisis de seguridad en cada PR, ayudando a identificar y mitigar riesgos asociados a las bibliotecas de terceros utilizadas en el proyecto.

\vspace{0.25cm}

\textbf{\underline{Supabase}}: Plataforma que provee una capa de acceso a la base de datos PostgreSQL con autenticación, 
APIs REST y almacenamiento. Se utilizó para simplificar la gestión y administración de la base de datos durante 
el desarrollo, aprovechando su interfaz visual para inspeccionar y manipular datos. Además de que provee \textit{tiers} 
gratuitos que se ajustaban a las necesidades del proyecto durante la etapa de desarrollo.

\vspace{0.25cm}

\textbf{\underline{Amazon Web Services (AWS)}}: Proveedor de infraestructura en la nube utilizado para el despliegue y 
operación del sistema en producción. Los servicios principales utilizados incluyeron EC2 para el cómputo de los servidores, 
S3 para el almacenamiento de assets, Route 53 para la gestión de DNS y ECR para el almacenamiento de imágenes de contenedores.

\vspace{0.25cm}

\textbf{\underline{PostgresSQL}}: Se decidió utilizar esta base de datos para llevar el registros de los usuarios, el estado 
de sus balances, los mundos creados y los diferentes assets que iban cargando en nuestro servicio. La facilidad del lenguaje 
SQL para la creacion modelado de los datos, como asi tambien la familiaridad con el mismo, permitieron agilizar rápidamente 
el desarrollo.

\vspace{0.25cm}

\textbf{\underline{MongoDB}}: Para utilizar y mantener el estado de los jugadores entre cada mundo y zona. Se utilizo esta 
base de datos por su facil lectura y escritura, omo asi también guardar y almacenar de forma sencilla con un modelo no relacional 
y mas flexible, como son los schemas. El equipo pensó tambien, utilizar esta herramienta para guardar los mundos, en vez 
de optar por PostgresSQL.

\vspace{0.25cm}

\textbf{\underline{Docker}}: Para levantar, probar y testear el core service, como asi tambien desplegar
la imagen del servidor de mundos. Se opto por la herramienta de virtualizacion y contenerizacion \textit{Docker}. Principalmente,
por el amplio uso por los miembros del equipo, su facil uso a través de comandos y \textit{docker-compose} y su extensa
documentación que permite consultar de manera facil y rápida, si se presenta alguna dificultad.

\vspace{0.25cm}

\textbf{\underline{Git}}: Para el control de versiones, se usa la ampliamente usada herramienta \textit{git}. No solo por 
todo el mundo, sino tambien porque es la herramienta necesaria para utilizar \textit{Github}. Se uso tambien \textit{git
submodules}, para gestionar el \textit{shared package}.

\vspace{0.25cm}

\textbf{\underline{Pre-Commit}}: \textit{Framework} para la gestión de hooks de Git ejecutados antes de cada commit. Se 
configuró para correr automáticamente \textit{linters}, formateadores y validaciones sobre el código antes de que este sea 
registrado en el repositorio, garantizando que todo el código commiteado cumpla con los estándares de calidad y estilo definidos 
por el equipo.

\vspace{0.25cm}

\textbf{\underline{Git Leaks}}: Herramienta de seguridad integrada en el pipeline de \textit{Github actions} que escanea 
el historial y los cambios del repositorio en busca de secretos expuestos accidentalmente, como claves de API, \textit{tokens} o 
credenciales. Su inclusión como control automático en cada PR ayudó a prevenir filtraciones de información sensible en el código fuente.
Adicionalmente, se añadió como parte de los pre-commit hooks, para evitar que secretos sean commiteados al repositorio.

\vspace{0.25cm}

\textbf{\underline{Code Coverage}}: Herramienta utilizada para la generación de reportes de cobertura de código. 
Se integró en el pipeline de CI para generar dichos reportes de cobertura en cada ejecución, permitiendo al equipo identificar 
áreas del código sin cobertura y mantener un umbral mínimo de calidad en las pruebas del core service.

\vspace{0.25cm}

\textbf{\underline{Github}}: Se utilizo \textit{Github} para mantener de forma \textit{online} el repositorio de codigo,
debido a que es la mas usada por todos y es la que el equipo estaba familiarizado. \textit{Github} no fue utilizado para 
alojar el codigo. Sino que tambien para utilizar \textit{Github Projects} para gestionar dia a dia el proyecto, como asi 
tambien \textit{Github actions} para correr los controles automáticos, de \textit{linters}, \textit{formaters}, tests, 
despliegue y controles de seguridad.

\vspace{0.25cm}

\textbf{\underline{Vercel}}: Plataforma de despliegue utilizada para hospedar los frontends web del proyecto: el landing page 
y el backoffice. Permite desplegar aplicaciones de forma automática ante cada \textit{push} a la rama correspondiente, 
integrándose directamente con GitHub. Se eligió por su simplicidad de configuración, su plan gratuito suficiente para la 
escala del proyecto y la velocidad de los despliegues.

\vspace{0.25cm}

\textbf{\underline{Swagger}}: Herramienta utilizada para documentar y exponer de forma interactiva los \textit{endpoints} REST 
del core service. Permite visualizar y probar la API directamente desde el navegador, facilitando la integración entre el 
equipo de backend y los consumidores de la API. Se integró con Gin Gonic para generar la documentación de forma automática 
a partir de anotaciones en el código.
