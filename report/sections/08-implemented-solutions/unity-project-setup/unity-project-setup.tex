Unity es el motor de desarrollo utilizado para ambas aplicaciones principales del proyecto. El \textit{World Editor} (Creador de mundos) por un lado y el \textit{Game}
(proyecto de juego), que agrupa el cliente y el servidor en un mismo proyecto de Unity por otro. Se desarrollan como 
proyectos independientes, cada uno con su propia configuración, assets y código. Para compartir estructuras 
de datos comunes entre ambos proyectos, se utiliza un submódulo o paquete compartido denominado \textit{Shared Package}, 
que centraliza los DTOs e implementaciones de servicios que realizan llamadas externas al \textit{Core Service}, 
evitando la duplicación de código.

Internamente, cada proyecto se divide en módulos independientes mediante Assembly Definitions 
(\textit{asmdef}), que son unidades de compilación separadas. Esta separación reduce los tiempos de 
compilación, ya que Unity solo recompila los módulos afectados por un cambio, y establece límites explícitos 
de dependencia entre módulos, evitando acoplamientos no deseados.

\subsubsection{Build Assembly Definitions}

Ambos proyectos se estructuran en tres módulos: \textit{Core}, \textit{Gameplay} y \textit{User Interface}, 
cada uno compilado como un assembly independiente. En el caso del proyecto de juego, esta estructura se 
separa en 3 assemblies para el cliente (\textit{Core}, \textit{Gameplay}, \textit{User Interface}) y 
2 assemblies para el servidor (\textit{Core} y \textit{Gameplay}), ya que el servidor no requiere elementos visuales

Esta separación garantiza que la lógica del cliente y la del servidor permanezcan aisladas, evitando dependencias 
cruzadas entre ambos.

A continuacion se describen las responsabilidades de cada módulo:

\begin{itemize}
  \item \textbf{Core}: Contiene la lógica central, librerías, interfaces y utilidades para que el módulo de Gameplay funcione. Esto incluye la gestión de repositorios internos y la comunicación entre distintos sistemas lógicos.
  \item \textbf{Gameplay}: Contiene la lógica de negocio en tiempo de ejecución, como la manipulación de objetos, comportamiento de entidades y reglas de juego.
  \item \textbf{User Interface}: Incluye todos los elementos visuales, como ventanas, paneles, menús y herramientas de usuario.
\end{itemize}

El código contenido dentro de estos módulos, pueden acceder a otros y tenerlos como dependencia, pero solo en el siguiente orden:

\begin{center}
    $Core \leftarrow Gameplay \leftarrow UI$ \textit{(e.g. Gameplay tiene como dependencia a Core)}
\end{center}

El proyecto de \textit{Game} cuenta además con dos módulos adicionales exclusivos de ese contexto:

\begin{itemize}
  \item \textbf{Common}: módulo compartido entre cliente y servidor, compuesto por los assemblies 
  \textit{Common.Core} y \textit{Common.Gameplay}. Centraliza el código que debe ser idéntico en ambos 
  lados, como utilidades, contratos, canales de eventos y otras definiciones compartidas.
  \item \textbf{Bot}: presente tanto en \textit{Core} como en \textit{Gameplay}, este módulo permite 
  desplegar bots en entornos de prueba de estrés, simulando múltiples jugadores realizando acciones 
  simultáneas en un mismo servidor para evaluar el rendimiento del sistema bajo alta carga. 
        Se compila como programa \textit{lightweight} aislado.
\end{itemize}

\subsubsection{Inyección de dependencias con \textit{VContainer}}

\textbf{VContainer}: Librería de inyección de dependencias para Unity utilizada como contenedor 
de inversión de control (IoC) del sistema. Permite declarar y resolver dependencias de forma explícita, 
desacoplando la construcción de objetos de su lógica de negocio. Esto facilita las pruebas de los 
componentes, reduce el acoplamiento entre módulos y centraliza la configuración del ciclo de vida de 
los objetos, reemplazando el uso de singletons y referencias estáticas propias de proyectos Unity 
sin arquitectura definida.

\subsubsection{Manejo del flujo de inicialización}

El primer módulo base para cada proyecto, tanto \texttt{Game} como \texttt{World Editor} es el \texttt{Core}.
En ambos, está conformado principalmente por clases que perduran en memoria durante la escena y pueden ser 
utilizadas por múltiples recursos. 

Cada proyecto tiene sus respectivos \textit{Entry Points}, que se encargan de iniciar e instanciar los 
recursos necesarios para el funcionamiento del proyecto, como servicios, gestores, controladores, 
y preparar la escena para su funcionamiento.

\vspace{0.25cm}

Dentro de estos hay elementos de como datos/valores fijos ya inicialmente configurados para el correcto 
funcionamiento. Por otro lado también otro recursos importantes son los eventos. 
Todos los eventos formalizan un \textit{event channel}, que es un canal de comunicación entre distintos 
componentes o sistemas, invocando y suscribiendose a estos eventos, de esta forma se evita el acoplamiento
entre clases.

\vspace{0.25cm}

Más adelante se describirá con más detalle la implementación del cliente, servidor y editor de mundos, 
con respecto a sus módulos restantes, pero la estructura base que contiene \texttt{Core}, de 
cada uno de estos proyectos, en esencia es la misma.
